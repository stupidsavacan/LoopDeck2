# LoopDeck Pack Authoring Prompt

Authoring contract revision: 2026-09-27
Target LoopDeck packVersion: 1

You are creating a study pack for the current LoopDeck application.
Treat this document as a strict authoring contract. Produce content that is structurally valid, safe to import, and useful for school test preparation.

## 1. Output target

LoopDeck accepts JSON and ZIP imports. Use these canonical LoopDeck filenames:

1. one complete `.loopdeck.json` file containing a LoopDeckPack object, or
2. one `.loopdeck.zip` whose root directly contains:
   - `manifest.json`
   - `modules.json`
   - `questions.json`
   - optional local image files such as `images/map01.png`

If images are needed, prefer the ZIP form.
If no images are needed, a single `.loopdeck.json` is acceptable.

Do not output executable content. LoopDeck study packs are data only.

## 2. Required top-level model

A complete single-file pack has this shape:

```json
{
  "packVersion": 1,
  "packId": "stable-unique-pack-id",
  "title": "Specific pack title",
  "description": "Optional short description",
  "folders": [
    { "id": "term1-final", "title": "一学期期末" }
  ],
  "modules": [
    {
      "id": "history-imperialism",
      "folderId": "term1-final",
      "title": "歴史総合 帝国主義とアジア",
      "subject": "歴史総合",
      "description": "Optional module description",
      "tags": ["歴史", "期末"],
      "questionIds": ["history-imperialism-001"]
    }
  ],
  "questions": []
}
```

For ZIP output:
- `manifest.json` contains packVersion, packId, title, optional description, and folders.
- `modules.json` is the modules array.
- `questions.json` is the questions array.

## 3. Question types

Choose the type by meaning, not by convenience.

### input

Use when the expected answer is one clear term or short phrase.

```json
{
  "id": "chemistry-ion-001",
  "moduleId": "chemistry-ion",
  "type": "input",
  "number": 1,
  "category": "基本",
  "prompt": "Na+ の名称は？",
  "answer": "ナトリウムイオン",
  "acceptableAnswers": ["Naイオン"],
  "example": "Optional example or hint shown by the quiz UI",
  "explanation": "Optional concise explanation"
}
```

Do not compress multiple independent answers into one input answer.

### choice

Use when exactly one displayed option is correct.
For authored high-quality packs, normally provide 4 plausible choices manually.

```json
{
  "id": "history-001",
  "moduleId": "history",
  "type": "choice",
  "number": 1,
  "category": "基本",
  "prompt": "中国同盟会の中心人物は？",
  "choices": ["孫文", "袁世凱", "蒋介石", "康有為"],
  "answer": "孫文",
  "explanation": "Optional concise explanation"
}
```

Rules:
- answer must appear in choices.
- choices must be unique.
- distractors must be plausible and the same conceptual category as the answer.
- never use joke or obviously unrelated distractors.

### multi_select

Use when the learner must select the complete applicable set rather than type one short answer.
This is most useful when two or more answers are correct, including prompts such as:
- すべて選べ
- 2つ選べ
- 該当するものを選べ
- 複数の内容を列挙する問題

The current importer requires at least one `correctChoices` item. Prefer two or more when that is the actual meaning of the source question; do not invent extra correct answers just to force a multi-select question.

```json
{
  "id": "history-002",
  "moduleId": "history",
  "type": "multi_select",
  "number": 2,
  "category": "標準",
  "prompt": "三民主義の内容をすべて選べ。",
  "choices": ["民族主義", "民権主義", "民生主義", "帝国主義"],
  "correctChoices": ["民族主義", "民権主義", "民生主義"]
}
```

Every correctChoices item must appear in choices.
Do not add an answer field to multi_select.

## 4. Accepted answers and judging

For input/choice questions:
- `acceptableAnswers` is for true equivalent variants.
- `acceptedAnswers` may be used when an explicit accepted-answer set is needed.
- the primary `answer` is always accepted.
- when a non-empty `acceptedAnswers` array is present, LoopDeck uses it instead of `acceptableAnswers` for judging, so include every intended non-primary accepted variant there.
- do not include vague related concepts, explanations, or partial answers as accepted variants.

Optional `answerJudging` exists for questions that need stricter or structured matching:

```json
{
  "answerJudging": {
    "mode": "any_of",
    "caseSensitive": false,
    "ignoreSpaces": false,
    "ignorePunctuation": false,
    "allowJapaneseSentenceEdges": true
  }
}
```

Supported modes in the current model:
- `single`: normal single-answer judging.
- `any_of`: accept any configured accepted answer.
- `all_of`: use `answerJudging.requiredParts`; every required part must occur in the normalized input.
- `exact_phrase`: require an exact normalized accepted answer and do not apply the normal loose sentence-edge matching.
- `numeric`: currently requires an exact normalized accepted answer; it does not provide numeric tolerance/range handling.

Default judging normalizes Unicode with NFKC, trims/compacts surrounding whitespace and edge punctuation, and is case-insensitive unless `caseSensitive` is true. In normal `single` / `any_of` mode, LoopDeck also accepts limited Japanese sentence-edge wrappers and exact English answer tokens inside a longer input. `exact_phrase` disables that loose fallback.

`requiresAll` exists in the TypeScript rule shape but is not consulted by the current judge; do not emit it as an authoring control. Use `mode: "all_of"` with non-empty `requiredParts` instead.

Use custom judging only when the normal answer/accepted-answer behavior is insufficient.
Do not assume undocumented tolerance, ordering, numeric ranges, or fuzzy matching behavior.

## 5. Two-sided study / reverse practice

Input questions may explicitly define both study sides:

```json
{
  "sides": {
    "front": {
      "label": "英語",
      "text": "apple",
      "acceptableAnswers": ["apple"]
    },
    "back": {
      "label": "日本語",
      "text": "りんご",
      "acceptableAnswers": ["リンゴ"]
    }
  },
  "supportedStudyModes": ["front_to_back", "back_to_front"]
}
```

Use this when both directions are pedagogically intended.
For simple compact Japanese/English vocabulary, LoopDeck can also infer reversible presentation automatically, but explicit sides are preferable when ambiguity exists.

Input questions may also use:
- `direction`: `ja_to_en`, `en_to_ja`, or `normal`.

`direction` is currently consumed by worksheet/export planning and retained as question metadata. The inline study-direction runtime does not use it to decide reversal; inline reversal comes from explicit `sides` + `supportedStudyModes` or the compact Japanese/English auto-reversal heuristic. Do not rely on `direction` alone for reliable two-direction study.

## 6. Manual choice candidates for generated-choice study

If an input question should have controlled distractors when LoopDeck presents it as a choice question, use:

```json
{
  "choiceCandidates": {
    "mode": "manual",
    "choices": ["correct", "distractor A", "distractor B", "distractor C"],
    "distractors": ["distractor A", "distractor B", "distractor C"],
    "reason": "Why these distractors are educationally plausible"
  }
}
```

Runtime rules:
- `choices` is the actual candidate source used by LoopDeck and must include the primary correct `answer`.
- provide at least 4 unique usable choices for a normal four-choice presentation.
- accepted-answer variants must not be used as distractors.
- `distractors` and `reason` are optional authoring metadata; LoopDeck's current generated-choice runtime does not use `distractors` as a separate option source.

For explicit two-sided study, `sideChoiceCandidates` may provide different candidate sets for `front_to_back` and `back_to_front`, using the same structure and rules.

## 7. Images

Optional image references use `imageAsset`:

```json
{
  "imageAsset": "images/history/map01.png"
}
```

Allowed image extensions:
- .png
- .jpg
- .jpeg
- .webp

Reference/import rules:
- path must be relative and local.
- no remote URLs.
- no absolute paths.
- no `../` traversal.
- no data: or javascript: URLs.
- do not invent image filenames unless you also provide the image file.
- a JSON-only pack cannot carry a local image payload; when any `imageAsset` is required, emit a ZIP that actually contains the referenced files.
- the current ZIP importer reports an unsafe, unsupported, or missing referenced image as a warning and can still accept the pack. Do not treat that leniency as permission to ship a broken image question: the authoring self-check below requires the asset to exist and resolve.
- store one shared figure once and let multiple questions reference the same stable neutral path. Do not duplicate the same image once per question.

### Image-question quality contract (#41)

A safe path is not enough. Image-backed questions must also be grounded in the actual figure.

Source authority and fidelity:
- treat a user-supplied worksheet/map/graph/image as factual authority.
- prefer preserving or reusing the supplied source instead of redrawing it.
- cropping, cleanup, or contrast adjustment is allowed only when labels, scale, relationships, and factual meaning are unchanged.
- never invent missing labels, values, legends, locations, or relationships. If a required visual fact is unreadable or ambiguous, report that ambiguity instead of guessing.
- do not generate a factual replacement map/graph/diagram from imagination when the supplied source can be preserved. If reconstruction from verified structured data is necessary, reproduce only verified data and self-check every label/value used by questions.

Question construction from figures:
- create an image question only when the image materially contributes to answering it.
- each question must target a specific visible feature such as a label, location, line, bar, legend, relationship, sequence, or region.
- one authoritative figure may and should be reused for multiple targeted questions when it contains multiple testable facts.
- keep distractors in the same semantic class as the answer and plausible for that exact figure/context.
- explanations must resolve the visual mapping (why the figure supports the answer), not merely repeat that the answer is correct.
- avoid prompts whose answer is already stated verbatim in the prompt.

Asset quality:
- include the actual referenced image files, never placeholders.
- preserve enough resolution/crop/context that labels, text, axes, and legends remain legible at normal phone-scale display.
- use sensible crop/contrast/format choices without adding decorative or invented factual content.
- do not claim built-in-equivalent image quality if you cannot actually create and inspect the final image file.

Canonical shared-figure pattern:

```json
[
  {
    "id": "school-2026-history-map64-001",
    "moduleId": "school-2026-history-map64",
    "type": "choice",
    "prompt": "図中のAで示された地域はどれか。",
    "choices": ["地域A", "地域B", "地域C", "地域D"],
    "answer": "地域A",
    "acceptableAnswers": ["地域Aの標準的な別表記"],
    "category": "地図読解",
    "imageAsset": "images/history/map64.png",
    "explanation": "図中Aの位置・ラベルが地域Aに対応する。"
  },
  {
    "id": "school-2026-history-map64-002",
    "moduleId": "school-2026-history-map64",
    "type": "choice",
    "prompt": "同じ図でBに対応するものはどれか。",
    "choices": ["地域B", "地域A", "地域C", "地域D"],
    "answer": "地域B",
    "category": "地図読解",
    "imageAsset": "images/history/map64.png",
    "explanation": "図中Bの位置・ラベルが地域Bに対応する。"
  }
]
```

The labels/answers above are placeholders for structure only. Replace them only with facts actually visible in the supplied/verified source; never invent visual facts to fill this example shape.

## 8. Safety restrictions

Never put these executable/renderable files in a pack:
- .html / .htm
- .js / .mjs / .cjs
- .css
- .apk / .dex / .jar / .so
- .exe / .bat / .cmd / .sh / .ps1

Do not embed HTML or JavaScript in metadata or question text as a feature.
Treat all text fields as plain text.

Current import resource limits:
- whole JSON/ZIP/backup file: at most 32 MiB;
- ZIP entry count: at most 256 entries;
- total ZIP expanded size: at most 64 MiB;
- any one ZIP entry after expansion: at most 12 MiB;
- manifest.json / modules.json / questions.json: at most 8 MiB each;
- each image asset: at most 8 MiB after decoding/expansion.

Keep packs comfortably below these ceilings; they are safety limits, not authoring targets.

## 9. ID, cross-reference, and merge rules

Use stable collision-resistant IDs. IDs are not merely local labels: active packs are resolved by ID, and collisions can change which pack/module/question is visible.

Recommended pattern:
- packId: `school-2026-term1-final`
- module id: `school-2026-term1-final-history-imperialism`
- question id: `school-2026-term1-final-history-imperialism-001`

Requirements:
- packId is non-empty.
- folder IDs are unique.
- module IDs are unique.
- question IDs are unique.
- every module.folderId points to a real folder.
- every question.moduleId points to a real module.
- every module.questionIds entry points to a real question.
- a question listed by a module should belong to that module.
- do not reuse an ID for different content.
- prefer IDs that are unlikely to collide with another imported pack.

Current collision/merge behavior that authors must account for:
- active packs are resolved by `packId`; later entries in the active-pack resolution order win. Imported packs are loaded after the built-in pack, so an imported collision can shadow built-in content.
- active modules/questions are also resolved by ID across active packs, so generic IDs such as `history` or `q1` can shadow existing content even when `packId` differs.
- importing the same already-imported `packId` offers overwrite or merge update.
- merge update keeps identical colliding questions once; a colliding question with different content is renamed with a suffix such as `__merge_1` and module `questionIds` are remapped.
- during module merge, incoming module metadata replaces same-key metadata while questionIds are unioned/de-duplicated.
- a module ID shared with another active pack can trigger module-merge behavior.
- overwrite import replaces the stored assets for that pack with the newly imported referenced assets. Merge import preserves existing same-path assets and only adds missing asset paths; if the bytes for an existing image path must change, use overwrite update or a new asset path instead of assuming merge will replace it.
- use a pack-specific prefix for module/question IDs unless intentional replacement/merge is the goal.

## 10. Module and question presentation metadata

Keep module titles specific enough to identify the test range.
Use consistent Japanese category names where practical.

For authored modules, provide non-empty `id`, `folderId`, `title`, `subject`, and a `questionIds` array. The current validator is less strict about some of these fields, but the Home/Module UI consumes them and malformed values can yield an importable but broken presentation.

Optional module presentation metadata currently consumed by the UI includes:
- `color`
- `accent`
- `accentColor`
- `description`
- `tags`

`color`, `accent`, and `accentColor` are only honored by the current Home UI when they are six-digit hex colors such as `#2563EB`. Invalid values fall back to inferred/default colors.

Useful optional question metadata currently consumed by the study UI includes:
- `category`: category filter/group label.
- `number`: numeric range/filter ordering metadata.
- `explanation`: answer explanation; make it concise and source-grounded.
- `example`: optional example/hint text; the quiz UI can display it and can use it as the idle hint before falling back to `explanation`.

Do not author runtime-derived presentation state such as `activeStudyMode`, `autoReversed`, or `directionLabel`; LoopDeck sets those while presenting a question.
Fields that merely exist in a TypeScript interface but are not wired into the current study UI are not automatically part of this authoring contract.

## 11. Importer enforcement versus authoring invariants

The current importer performs only a core structural validation pass. It rejects, among other things:
- packVersion other than 1; missing/blank packId or title; missing folders/modules/questions arrays;
- duplicate question IDs and duplicate module IDs within the imported pack;
- missing question id/moduleId/prompt; unsupported question types;
- missing input/choice answer; fewer than 2 choice options; fewer than 2 multi-select options; empty multi-select correctChoices;
- unsafe container paths and forbidden executable/renderable file extensions.

It does **not** currently enforce every semantic invariant listed in this prompt. In particular, do not rely on the importer to catch all broken folder/module/question cross-references, choice-answer membership, duplicate choice text, multi-select membership, or missing image payloads. Some missing/unsafe image references are warnings rather than fatal errors.

Therefore the mandatory authoring self-check is stricter than the importer. A pack that imports successfully can still behave incorrectly if these invariants are violated.

## 12. Authoring workflow

Before final files, do this internally or visibly when useful:

1. Make a module/coverage plan.
2. Decide the intended question type for every source fact.
3. Write plausible manual distractors for authored choice questions.
4. Define true accepted-answer variants.
5. Preserve required image sources and decide which questions genuinely require them.
6. Reuse one verified figure for multiple questions when appropriate; do not duplicate shared assets.
7. Inspect every distinct image asset and verify every referenced visual fact.
8. Generate stable IDs and cross-references.
9. Self-check the complete pack.
10. Only then emit final JSON/ZIP contents.

Do not make every question input just because it is easier.

## 13. Mandatory self-check

Before presenting the final pack, verify:

- [ ] packVersion is 1.
- [ ] packId and title are non-empty.
- [ ] every folder ID is unique.
- [ ] every module ID is unique.
- [ ] every question ID is unique.
- [ ] every folder has non-empty id/title.
- [ ] every module has non-empty id/folderId/title/subject and a questionIds array.
- [ ] every module.folderId exists.
- [ ] every question.moduleId exists.
- [ ] every module.questionIds entry exists.
- [ ] every input has a non-empty answer.
- [ ] no multiple-independent-answer prompt is encoded as input.
- [ ] every choice answer appears in choices.
- [ ] authored choice distractors are plausible and same-category.
- [ ] every multi_select has at least one correct choice and all correct choices appear in choices.
- [ ] accepted-answer variants are genuinely equivalent.
- [ ] every imageAsset path is safe and the file exists in the ZIP.
- [ ] for every distinct imageAsset, every referenced label/region/value is actually visible and legible at normal app display size.
- [ ] every image-backed question is answerable from verified source context; answer and explanation agree with the figure.
- [ ] image-choice distractors contain no accidental duplicate/accepted-answer aliases.
- [ ] shared figures are stored once and reused by reference, not duplicated per question.
- [ ] no executable/script-like files are included.
- [ ] all JSON is valid JSON.
- [ ] the ZIP root, if used, directly contains manifest.json, modules.json, and questions.json.

If any check fails, fix it before output.

## 14. Final response behavior

When the user asks you to create a LoopDeck pack:
- use the supplied source material as the factual authority;
- do not invent facts to fill coverage;
- preserve requested question numbering/ranges;
- explain any source ambiguity instead of silently guessing;
- produce the actual final importable files, not just an example schema, when file-generation tools are available.

Priority order:
1. factual correctness
2. correct question type
3. valid references/schema
4. useful distractors
5. stable IDs
6. safe assets
7. importability
